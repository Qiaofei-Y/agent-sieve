AI / Agent Intrusion Traces: A Self-Test Purple Team Playbook

On your own home or corporate network, stand up detection vantage points at minimal cost, then play the attacker yourself to verify whether "anomalous AI/agent behavior" can actually be caught — and what can slip past it. From the defender's (blue team) point of view.

Scope Only networks you own or are authorized to test Approach Purple Team · attack and detect yourself Updated 2026-10-19
中文
Authorization boundary. Every "attack" action in this playbook is run only against your own devices, on a network you own or have written authorization to test, for the purpose of validating detection. Never use any of these steps against third-party networks, other people's devices, or unauthorized targets.
01

First, split "AI intrusion" into three threat models

Their detectability at the network layer differs enormously; lumping them together means you miss the real ones and drown in false positives.

A

External AI crawlers scraping your services

GPTBot / ClaudeBot / PerplexityBot and friends crawl your internet-facing NAS, blog, or reverse proxy. Includes spoofed crawlers — a UA that says GPTBot while the IP is nowhere in the official ranges.

Difficulty · Easy
B

Shadow AI exfiltration

Some device or person on the LAN keeps feeding data to an LLM API (api.openai.com and the like), or a locally running agent is sending content out. The first class you should tackle.

Difficulty · Medium
C

Autonomous agent / AI-driven intrusion

On the wire it looks almost identical to an ordinary scripted intrusion — the AI lives in the attacker's cloud, and what reaches you is just requests. What gives it away is the "machine cadence," not the "AI" itself. Don't overclaim.

Difficulty · Hard
02

Four vantage points, and what each one can see

At the router you only have metadata. Ordered from lowest to highest deployment cost; the colors are reused in the test matrix later.

DNS

Pi-hole / AdGuard Home

Cost · Minimal

Acting as network-wide DNS, it logs every domain query from every device. The fastest way to catch threat B and local agents that use the system resolver.

  • Match against a known LLM API / agent domain list
  • Surface never-before-seen new domains (shadow source)
Can seethe queried domain, which device, how often
Can't seeclients using DoH/DoT (bypass it outright)
FLOW

Router connection logs / conntrack

Cost · Low

Per-connection IP:port, byte counts, timestamps. Even when DNS is bypassed, the IP layer still leaves traces — reverse-look up the IP to attribute it to an LLM vendor.

  • Regular intervals of periodic callbacks (beaconing)
  • Abnormal outbound volume / full-site traversal
Can seepeer IP, traffic size, cadence
Can't seethe actual content or specific URL
TLS

Mirror port + Zeek (JA4 fingerprint)

Cost · Medium

A switch SPAN port mirrors traffic to a Raspberry Pi running Zeek, which extracts the JA4 fingerprint from the TLS handshake — determined by the network stack, immune to a spoofed UA.

  • The fingerprint of python/Go/curl ≠ a real browser
  • SNI (unless the peer enables ECH), certificates, QUIC
Can seewhether the client is a script, and the domain it connects to
Can't seebrowser fingerprints spoofed by curl_cffi
HOST

Endpoint · OpenSnitch / Little Snitch

Cost · Medium (needs install)

Where you can install on the endpoint, this is the only vantage point that ties traffic to a process — which binary, which script is reaching out.

  • Per-process outbound allowlist / alerting
  • Content before encryption (visible on the host)
Can seethe process, command line, full destination
Can't seedevices that can't run an endpoint (IoT, guest machines)
03

Two physical limits you must accept up front

Fail to face these two, and every detection that follows is self-deception.

① Without MITM you only have metadata

Traffic is TLS-encrypted. Unless you install your root certificate on every device to do man-in-the-middle decryption, you will never see "which page was read, what content was sent." Network-wide MITM is not advisable at home (too destructive, too risky), so position the product as "anomalous-behavior detection," not "content inspection."

② DoH/DoT and ECH are narrowing your view

  • DoH/DoT: a client with its own encrypted DNS bypasses Pi-hole outright. This is enemy number one — you must block port 853 at the firewall, intercept known DoH resolver domains, and force DNS back into your own hands, or the DNS layer is effectively useless.
  • ECH (RFC 9849, finalized 2026-03) encrypts the SNI, hiding even the domain. Today almost only Cloudflare has shipped it server-side, so most sites' SNI is still visible — but this is a one-way trend; don't bet your architecture on SNI staying visible.
  • Fingerprints can be forged: curl_cffi --impersonate chrome / tls-client can replicate a browser's JA4. So JA4 catches the lazy agent, not the deliberately disguised one — it's one signal, not a verdict.
04

Start minimal: a four-stage rollout

Each stage delivers value on its own; you don't have to wait for the full build-out.

S0
One afternoon

Pi-hole as network-wide DNS + a domain list

Point the router's DHCP DNS at Pi-hole and match the query log against ~40 known LLM API / agent domains. Zero extra hardware (a Raspberry Pi or a spare machine will do).

✓ Threat B · Shadow AI✓ Local agents (system DNS) 
# Pull LLM / agent traffic from the Pi-hole query log (minimum viable)
sqlite3 /etc/pihole/pihole-FTL.db \
  "SELECT datetime(timestamp,'unixepoch','localtime') t,
          client, domain
   FROM queries
   WHERE domain LIKE '%openai.com'
      OR domain LIKE '%anthropic.com'
      OR domain LIKE '%generativelanguage.googleapis%'
      OR domain LIKE '%api.perplexity.ai'
   ORDER BY timestamp DESC LIMIT 50;"
S1
One day

Verify whether crawlers are genuine on exposed services

Against the access logs of your internet-reachable reverse proxy / NAS, pull the vendors' official IP-range JSON for forward verification — if a UA claims to be GPTBot but the source IP isn't in openai.com/gptbot.json, it's an impostor.

✓ Threat A · Real vs. fake crawlers 
# Official IP-range JSON (fetch on a schedule, don't hardcode)
openai     → https://openai.com/gptbot.json
anthropic  → https://claude.com/crawling/bots.json
perplexity → https://www.perplexity.ai/perplexitybot.json

# Ready-made open-source tools: daily-updated IP ranges + verification scripts
github.com/ramhee98/ai-crawler-ipranges
github.com/ayronjins/ai-crawler-verify
S2
One weekend

Mirror port + Zeek: catch scripted clients and callbacks

If you have a managed switch, enable a SPAN port; if not, use a software router that supports mirroring, and feed the traffic to Zeek on a Raspberry Pi. Take JA4 from ssl.log and compute callback cadence from conn.log.

✓ The detectable part of threat C✓ Script vs. browser 
# Start Zeek listening (Zeek 5.2+ supports QUIC natively)
zeek -i eth0 LogAscii::use_json=T

# Find non-browser JA4 in ssl.log (compare against python/go/curl fingerprint libs)
jq -r 'select(.ja4 != null) | [.ts,.server_name,.ja4] | @tsv' ssl.log
S3
Incremental

Three-way aggregation + scoring + alerting

Aggregate the DNS / FLOW / TLS sources per device, apply the scoring rules below, and push an alert when the threshold is exceeded (Telegram / email). This is the step that makes it feel like a product.

✓ Sustainable operations

Scoring rules: turn signals into a single number

Any single signal false-positives. Accumulate weights per device within a time window and only alert above the threshold, to keep the noise down.

+40
Non-browser JA4
python/go/curl stack connecting out directly
+30
LLM API domain
initiated by a device that isn't a known AI client
+25
Regular callbacks
even intervals + low-jitter beaconing
+20
Domain fan-out burst
many unfamiliar domains in a short window
+20
Spoofed crawler

+15

Suggested thresholds: on a home network, ≥ 50 pushes a notification, ≥ 80 needs human review; on a corporate network, tune per device against its baseline. Run observation-only mode for two weeks first to build each device's normal profile, then turn on alerting — otherwise your first week will be buried by your own normal traffic.

07

Three things that differ on a corporate network

  • Vantage points are easier to get: with MDM you can roll out endpoints (HOST) across the fleet, and a managed switch gives you a ready SPAN port — an advantage the home network lacks.
  • Baselines matter more: employees already use a pile of SaaS, so the LLM-domain hit rate is naturally high. The focus shifts from "is it happening at all" to "which device is abnormally busy, and which account is sending data out in bulk outside working hours."
  • Compliance comes first: monitoring employee traffic touches privacy and labor law. Clear it with internal policy and informed consent before deployment — don't treat the technical design as a ready-to-ship solution.
